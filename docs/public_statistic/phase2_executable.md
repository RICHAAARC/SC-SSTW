# Phase2 executable preparation

This is an executable proposal, not a GPU result. No model weights were downloaded and no GPU/model experiment was run during preparation.

The Colab entry is `notebooks/public_statistic_phase2_gpu.ipynb`, adapted from the previously working `stage2_local_temporal_warp.ipynb` and `stage2_off_baseline.ipynb` workflow: independent Drive mount, ordinary pip install retaining Colab CUDA PyTorch, source directory, one supervised subprocess, Drive output, no overwrite. The notebook fetches the named development branch from GitHub and records its actual HEAD without an equality gate. This entry is published under separate source-publication authorization; GPU execution remains a separate user decision. No ZIP upload is required. There is no additional unlock switch. An optional backup ZIP can be built with `python -m experiments.public_statistic.build_phase2_package --output /absolute/new/public_statistic_phase2_source.zip`.

The loader reuses the full WanPipeline.from_pretrained → encode_prompt → prepare_latents sequence and the historical independently loaded FP32 AutoencoderKLWan. It releases the text encoder, keeps transformer BF16 and VAE FP32 resident, and does not install old CPU-offload hooks. This change is necessary for a differentiable remaining solver trajectory. Prompt embeddings use transformer precision, initial latent is FP32, and actual VAE geometry determines representable input sizes. Loaded model identifier/revision request, dependency versions, scheduler configuration/timesteps and actual dtypes are recorded; none are exact-match/version gates.

The three-arm trial uses 50 steps, CFG5, seed1275, 320×512,49frames,8fps. The common prefix completes indices0–46; its unchanged complete scheduler state is cloned into OFF1/OFF2/Y_MINUS tails. Feedback follows completed47 and48, forecasting all2/1 remaining steps through FP32 floating VAE and the same public F. Fixed target is F(OFF1)-2/255 in Y; fixed reference is OFF1 floating terminal RGB. eta10, per-update RMS0.001*r0, cumulative sum0.002*r0, r0 the fixed prefix RMS. Acceptance is strictly decreased full terminal MSE and whole-clip RGB RMSE≤3/255. Per-frame and worst-frame quality are diagnostics only. A normal loss/quality rejection advances the original latent and full solver history normally.

124 transformer calls =94 common prefix+12 OFF tails+6 controlled normal steps+12 terminal forecasts. At most7 VAE calls and2 autograd backward calls; no checkpoint/recompute, one attempt, no retry. At most3 MP4/147 frame slots. A strict feedback mode propagates OOM, nonfinite, zero gradient, broken graph and callback exceptions to a fatal worker stop; it cannot turn these into ordinary rejection. Transformer/VAE/backward calls are reserved before invocation, including failed attempts. The launcher applies a1800-second process-group deadline including worker import/download/load/encode/backward/codec, records process-tree RSS as best-effort diagnostics without a host-memory limit; unavailable diagnostics do not stop the worker. It kills all descendants on deadline or worker failure. CUDA allocator is capped at22GiB; external CUDA allocations are outside PyTorch allocator accounting, so actual device OOM remains a fatal stop. Three arms and all147 rows are created before model loading; completed rows survive failures and pending rows remain visible.

Future execution: `python -m experiments.public_statistic.run_phase2 --config configs/public_luma_phase2_gpu.json --output /absolute/new/run03`. Do not invoke this as a local preparation check: it loads real weights. The proposed device is one BF16-capable L4 24GiB. Real Wan autograd connectivity, forward/backward memory, throughput, codec statistics and outcome remain unverified. MP4 readback uses the public reader and reports quality versus fixed floating OFF1 separately from floating acceptance; no codec success gate is inferred from candidate acceptance.

Wan input dtype is taken from patch_embedding.weight, because its root scale_shift_table may remain FP32 even when the input Conv3d is BF16. Both CFG passes share this differentiable cast; solver latent and VAE remain FP32. run03 preserves run01/run02 failures.
